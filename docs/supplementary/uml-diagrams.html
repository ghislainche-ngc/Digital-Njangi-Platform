Sequence Diagram 1

User Registration & Login with OTP Verification

Traces the full authentication flow: a new user submits their credentials to the Frontend, which proxies to the REST API (POST /auth/register). AuthService hashes the password, persists via DBConnect to Supabase, and triggers an OTP via SMS/Telegram. On OTP verification, AuthService issues a signed JWT returned to the client.

Create Njangi Group & Invite Members

A President creates a new group by submitting settings to the API. GroupService persists the group and auto-creates a Membership record (role: president). The President then invites new members by phone number; GroupService generates a tokenised Invitation record and dispatches an SMS/WhatsApp link. Invited users follow the link to accept and are enrolled with the "member" role.

Sequence Diagram 3

Monthly Contribution Collection — Automated MoMo Deduction

The System Scheduler (cron job) triggers ContributionScheduler at the start of each contribution period. ContributionService creates pending Contribution records for all active members, then invokes MTNMoMoService to charge each registered wallet. On success, status is updated to "paid" and a WhatsApp/SMS confirmation is sent. On failure, the system retries up to 3 times, then marks the contribution "failed" and notifies the Treasurer.

Sequence Diagram 4

Payout Execution with Eligibility Checks

Treasurer initiates a payout. PayoutEngine performs a multi-step eligibility checklist before disbursing: (1) pot threshold collected, (2) recipient has no unpaid fines, (3) recipient's MoMo wallet is linked, (4) President has approved. On all-clear, PayoutEngine calls PaymentProvider to disburse, then RotationEngine advances to the next recipient, and all members are notified. Every step is audit-logged.

Fine Application (Automated) & Waiver (President)

A nightly PenaltyScheduler cron identifies overdue contributions and creates Fine records at the configured daily rate. Members are notified immediately. Later, the President may waive a fine via the API, providing a reason; the waiver is persisted and audit-logged for full traceability.

View Financial Report & PDF Export

The President requests a contribution ledger report for a given cycle. ReportService fetches all relevant data (contributions, payouts, fines, social fund) from Supabase via DBConnect, assembles a structured ledger, and delegates PDF rendering to PDFService. The generated PDF buffer is uploaded to Supabase Storage, and a short-lived signed download URL is returned to the client.

OOP Design Reference

Design Patterns Summary

NAAS applies eleven recognised Gang-of-Four (GoF) and enterprise design patterns across its domain and service layers. Each pattern solves a specific architectural concern, promoting extensibility, testability, and separation of concerns throughout the system.

Creational

Singleton

Guarantees a single shared database client instance throughout the application lifetime, preventing redundant connection overhead and race conditions on initialisation.

DBConnect._instance, getInstance()

Behavioral

Strategy

Encapsulates the three rotation algorithms (Fixed, Random Draw, President Decision) behind a common RotationStrategy interface. RotationEngine accepts any strategy at runtime without changing its own code, making it trivial to add new rotation modes.

RotationStrategy, FixedRotationStrategy, RandomDrawStrategy, PresidentDecisionStrategy, RotationEngine

Structural

Template Method

Abstract base classes PaymentProvider and NotificationService define the skeleton of algorithms (charge, disburse, send), leaving concrete steps to subclasses (MTNMoMoService, OrangeMoneyService, TelegramNotificationService, SMSNotificationService).

PaymentProvider, NotificationService and their concrete subclasses

Structural

Facade

PayoutEngine provides a single, simplified interface (execute()) that hides the complexity of orchestrating ContributionService, FineService, PaymentProvider, RotationEngine, NotificationService, and AuditService behind one cohesive call.

PayoutEngine.execute(), PayoutEngine.checkEligibility()

Behavioral

Observer (Event-Driven)

Domain events (e.g., CONTRIBUTION_PAID, PAYOUT_EXECUTED, FINE_APPLIED) are emitted and consumed by the NotificationService and AuditService, decoupling the source action from its side effects (notifications, logging).

AuditService.log(), NotificationService.send()

Structural

Repository

DBConnect acts as a generic repository, centralising all Supabase data-access operations (create, findAll, findOne, update, remove) so domain services remain agnostic of the underlying storage engine.

DBConnect.create(), findAll(), findById(), update(), remove()

Structural

Inheritance / Polymorphism

Abstract hierarchies (PaymentProvider, NotificationService, RotationStrategy) use inheritance to share contracts and polymorphism to allow runtime substitution of concrete implementations without altering calling code.

MTNMoMoService, OrangeMoneyService, TelegramNotificationService, SMSNotificationService

Creational

Factory Method (implicit)

RotationEngine selects and instantiates the appropriate RotationStrategy subclass based on group.rotation_type, centralising object creation logic and shielding callers from construction details.

RotationEngine.selectNextRecipient() → strategy instantiation

Behavioral

Chain of Responsibility

Eligibility checking in PayoutEngine.checkEligibility() is structured as a sequential chain of guards (threshold check → unpaid fines → wallet linked → president approval). Each guard either passes control forward or short-circuits with an error.

PayoutEngine.checkEligibility() guard chain

Behavioral

Command (Token-Based Invitation)

The Invitation entity encapsulates an "accept membership" command as a shareable, time-limited token. The token carries all information needed to execute the action independently of the originating session, enabling async out-of-band flows.

Invitation.send(), Invitation.accept(), Invitation.expire()

Structural

Service Layer (Application Services)

Business logic is encapsulated in dedicated service classes (AuthService, GroupService, ContributionService, FineService, ReportService, PayoutEngine) separate from controllers and data-access, following the Service Layer enterprise pattern for clean layered architecture.

AuthService, PDFService, AuthService._signToken()
